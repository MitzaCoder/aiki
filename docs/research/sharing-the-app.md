# Sharing the app

Research, 2026-11-09. **Recommendation: ship a local web app with a small installer and guided setup before building a desktop shell.** Each friend runs their own backend, repositories and provider account. Do not give friends access to the operator’s backend or publish an unauthenticated port.

Scope: source/docs inspection only; no install tests, provider requests, live-data access, deploys or code changes. Estimates below are engineering days for one person familiar with this repo, not promises.

## What T3 Code does

Sources were read at upstream main [`ad9e8711`](https://github.com/pingdotgg/t3code/tree/ad9e87111fd9b2f10ec320b4de0a6ad3a092278a). Main moves ahead of releases: latest stable observed was [v0.1.7, November 4](https://github.com/pingdotgg/t3code/releases/tag/v0.1.7); the [November 9 nightly](https://github.com/pingdotgg/t3code/releases/tag/v0.1.8-nightly.20261109.4429) introduces the single Welcome page. Do not assume every current-doc feature is in stable.

- **Distribution is all three, not either/or.** An Electron desktop app bundles its server runner; a CLI serves the web app locally; [app.t3.codes](https://app.t3.codes) is a hosted client, not hosted agent compute. Current preferred CLI install is `curl -fsSL https://t3.codes/install.sh | sh` (PowerShell equivalent on Windows), then `t3`. `npx t3@latest` still works as a try-it path and now offers to install the command. It requires Node for npx; the standalone installer does not require the user to install Node. [README](https://github.com/pingdotgg/t3code#installation), [install](https://github.com/pingdotgg/t3code/blob/main/docs/user/install.md).
- **First run discovers rather than starts blank.** Current main has one Welcome page: detected agents, optional recent project/history import, phone setup, and actionable Install/Sign in/Update controls. Claude setup opens a terminal with vendor commands; Codex offers managed ChatGPT setup or an existing CLI. Start needs one ready agent, but “Start without an agent” is available. Hosted web instead asks for T3 Connect and a computer. This replaces the older three-step wizard. [Welcome](https://github.com/pingdotgg/t3code/blob/main/docs/user/welcome-page.md).
- **Bring your own subscription, on the execution machine.** Claude uses Claude Code’s login/config through the official Agent SDK; Codex can use an existing authenticated CLI (`codex login`) or a managed runtime with “Connect with ChatGPT.” Detection uses the server’s PATH, version/auth checks and an explicit Binary path override. `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, provider-instance environment variables and Codex shadow homes support separate accounts. Credentials are not taken from the phone; installing a desktop GUI does not magically authenticate a remote server. CLI installers/version managers can also be used for provider updates. [Claude](https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-claude.md), [Codex](https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-codex.md), [providers](https://github.com/pingdotgg/t3code/blob/main/docs/user/install.md#providers).
- **Remote/mobile is a product feature.** `t3 up` chooses Connect, LAN or both; `t3 connect` means `t3 up --connect`. Connect uses account sign-in, including URL + short code over SSH, and a Cloudflare tunnel; T3’s relay arranges the link rather than proxying agent sessions itself. Free Connect currently links three machines; linked paid T3 Chat plans raise limits. Direct LAN/Tailscale pairing uses one-time URLs/QR codes, retained device sessions and revocation. Tailscale HTTPS and desktop-managed SSH are alternatives. Native iOS/Android apps are in stores; phones remain remote controls and need an awake host. Hosted web needs HTTPS/WSS; a QR code supplies neither reachability nor TLS. [Remote](https://github.com/pingdotgg/t3code/blob/main/docs/user/remote-access.md), [FAQ](https://github.com/pingdotgg/t3code/blob/main/docs/user/faq.md).
- **Storage has a documented home.** Default T3 home is `~/.t3`, overridable with `T3CODE_HOME`/`--base-dir`. Normal state is `userdata/statev2.sqlite`, `settings.json`, `keybindings.json`, attachments, logs and secrets; worktrees/caches/runtime downloads live elsewhere under T3 home. Service overrides are `~/.t3/service.env`; providers retain their own homes/auth. Uninstall preserves user state. [Paths](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/config.ts#L139), [service](https://github.com/pingdotgg/t3code/blob/main/docs/user/background-service.md).
- **Updates include the backend, not just the window.** Desktop has in-app updates and Stable/Nightly tracks. Current UI can coordinate provider, connected-server and desktop updates, with progress and failure/retry handling. `t3 update [version]` handles standalone installs; npx users stop and relaunch the desired version. Linux/macOS services can update remotely and roll back on failure; package-managed Nix/AUR installs update through their package manager. Incompatible protocol versions refuse connection with an update explanation. Updates can interrupt turns/terminals; supported threads resume by policy. [Updating](https://github.com/pingdotgg/t3code/blob/main/docs/user/updating.md).
- **OS support is qualified.** Desktop: macOS Intel/Apple Silicon, Windows x64/ARM64, Linux x64/ARM64 (`.deb`, AppImage; package-manager routes too). Standalone CLI releases omit Intel Macs: use desktop or source. Background services support Linux systemd user services and macOS launch-at-login, not Windows. WSL hosts are supported through desktop-managed server installation. Source is MIT, copyright T3 Tools Inc.; agent subscriptions still cost money. [Install](https://github.com/pingdotgg/t3code/blob/main/docs/user/install.md), [licence](https://github.com/pingdotgg/t3code/blob/main/LICENSE).
- **Do not copy its privacy defaults.** T3 currently sends product usage events by default, with hashed installation/account identifiers, model/provider and token totals; it also has separate relay/mobile diagnostics and optional agent-activity publication. Server telemetry opt-out does not disable every browser/mobile trace. Our app’s telemetry should stay off. [Telemetry](https://github.com/pingdotgg/t3code/blob/main/docs/user/telemetry.md).

### Quick user feedback

[T3’s homepage](https://t3.codes) quotes users praising the consistent multi-agent UI, Electron performance and seamless remote VM access. These are curated testimonials, not an independent user survey. Concrete issue reports show the costs of polished distribution:

- [#20871](https://github.com/pingdotgg/t3code/issues/20871), closed completed: Windows update unexpectedly asked users to pair the local environment; reports included an old WSL service owning the same data directory.
- [#19398](https://github.com/pingdotgg/t3code/issues/19398), closed not planned: saved host:port routes stopped working after a port change until re-pairing. Current docs describe multiple learned routes; this is historical feedback, not proof the current build still has the defect.
- [#21375](https://github.com/pingdotgg/t3code/issues/21375): report of nightly upgrades invalidating pairings and client/server incompatibility. [#33425](https://github.com/pingdotgg/t3code/issues/33425): confusion between linking environments and pairing a client.

Takeaway: keep machine identity, data-home ownership, credentials and addresses distinct. Explain update/connection failures and provide repair commands. Do not make users delete state to recover.

The core is more portable than deployment: data paths and bind address are configurable, and source can run with Bun without Nix/systemd. The blocker is the missing supported product install, not a mandatory rewrite.

### Security gate before sharing remotely

Treat each backend as **remote shell access with the server user’s filesystem and provider spending authority**, not a chat server. Friends should operate separate installations; the current model is not multi-tenant.

Minimum review/implementation work:

1. Authenticate HTTP/WebSocket access independently of Origin, including native clients, reconnects and sensitive RPCs. One-time, short-lived, single-use QR enrollment should create revocable per-device sessions, not a reusable URL master key. Bootstrap enrollment must require local approval/secret; never expose an unauthenticated network setup wizard.
2. Keep loopback default, validate Host/Origin against DNS rebinding/cross-site WebSocket attacks, require TLS for remote use, and document tailnet ACL/firewall scope. Tailscale narrows reachability but does not replace application permissions. Never suggest `0.0.0.0` alone or public router forwarding.
3. Review filesystem/terminal/project controls, credential-setting/login/log-out RPCs, artifact bearer URLs and preview rendering, frame/rate/resource limits, path traversal, SSRF opportunities and logs. A codemode sandbox does not sandbox the shell tools it can call. No “safe colleague read-only access” claim without server-enforced scopes.
4. Protect token/key files and backups; redact enrollment URLs, OAuth redirects and secrets from logs/support exports. Scope Android credentials to devices and use secure storage. Test revocation, restarts, origin rejection, expired/replayed enrollment, an Origin-less unauthorized client and protocol version drift.
5. Do not ship broad Firebase service-account credentials. Either defer native push, provision an appropriately restricted design per installation, or build a narrowly authenticated push broker. For independent web backends, consider per-backend push subscriptions/VAPID ownership instead of distributing one private key.

## Options and rough effort

Packaging estimates are **incremental after shared groundwork**: security/auth review + device sessions and client integration **5–9 days**; first-run readiness checks/sign-in/project/model flow + neutral defaults + basic docs **3–5 days**. These overlap some packaging work; do not add every table row together. Cross-OS surprises, external security assessment and provider-policy changes are not included.

| Option | Extra days | Benefits | Costs / fit |
| --- | ---: | --- | --- |
| A. One-command Bun package/installer + local UI | 3–5 | Fastest developer-friendly MVP; browser UI already exists; run foreground first, optional service later. | Publish a CLI with bundled static assets; Bun must exist or installer must install a pinned runtime with consent. `npx` does not make Bun-specific code run on Node: it would need a runtime launcher. Prefer `bunx` for friends who already have Bun, otherwise a reviewed release installer. |
| B. Desktop app bundling backend + UI | Electron 10–18; Tauri 15–25 | Familiar install, browser opening/PATH/service lifecycle hidden, good first-run affordances. Electron can reuse web UI. | Bundle a Bun sidecar, **not** a server rewritten for Electron’s Node. Signed/notarized installers, child lifecycle, auto-update, PATH/keychain differences and OS matrix. Tauri is smaller but Rust/sidecar/update/WebView integration costs more; existing Kotlin app remains separate. |
| C. `bun build --compile` binary + UI + optional service | 5–9 | No separately installed JS runtime; good server/SSH install; can underpin A or B. | “Single-file executable” is not automatically a fully static, dependency-free app. Prove pi workers, lazy SDK imports, Photon/WASM, codemode assets, SQLite and resource paths survive compilation; git/jj/zellij/toolchains remain external. Build/test each OS/arch/libc target; macOS signing still matters. |
| D. Docker image + local UI | 3–5 | Reproducible Linux/server runtime and pinned updates. | Poor default for friends editing host repos: UID ownership, mounts, credential access, SSH agent, GUI/browser tools, nested services and jj workspace paths. Docker Desktop prerequisite; container isolation disappears if given host socket/broad mounts. Offer later for deliberate VM/server users. |
| E. Hosted static UI + local server | 2–4 | UI updates centrally; closest to today’s architecture; no desktop shell. | Still needs A/C/D for agent host; secure backend endpoint, auth, TLS, local-network browser permissions/mixed-content handling and client/server compatibility. Hosted JS is trusted to control the host and can change without a backend update. Keep local bundled UI as the reliable default. |

[Bun compilation docs](https://bun.com/docs/compiler/executables) support embedded files and explicit worker entrypoints; this repo’s compilation has **not** been attempted. Spend a capped **1–2 day spike** before choosing C, not a week promising binaries that have not started successfully.

### Cross-cutting choices

- **Phones:** start with a Tailscale guide for each friend’s own computer/phone, HTTPS via Tailscale Serve and app-authenticated QR enrollment. Allow roughly **2–3 days** for guide/setup/diagnostics beyond auth. Private tailnet access is easiest operationally, not zero setup. QR code means enrollment, not a tunnel. Built-in tunnelling is **8–15+ days** plus account/relay operation, abuse controls, TLS and privacy/support costs; defer it. Optional desktop SSH can follow later.
- **Android:** prefer a stable, signed **release APK on GitHub Releases** for the initial few friends (**2–3 days** for signing/versioning/build/docs). Keep one backed-up signing identity so upgrades do not require uninstalling state. Sideloading has a warning and manual updates. Play internal testing (**3–5 days engineering**, account/review timing separate) gives controlled invitations and store updates; requires developer ownership, app signing, policy/privacy forms and permanent package-name choices. Do not promise instant store approval. A phone browser is enough for initial use; native push can be deferred.
- **Updates:** tagged releases with checksums (ideally signatures), a stable channel, version display and release notes. MVP explicit update command/manual install, restart confirmation, backup/migration policy, health check and previous-release rollback; do not move a user’s git bookmark. Keep data outside install trees. Later automatic download + user-approved restart. Retain capability negotiation and define supported web/Android/backend version ranges; distinguish binary rollback from incompatible data migration rollback.
- **Brand/licence/privacy:** choose a neutral public name after domain/package/trademark availability checks, not a name invented in this research. Keep old env/storage keys as migration aliases rather than losing existing devices. MIT is the simplest T3-like choice; Apache-2.0 adds an explicit patent grant; AGPL is a different reciprocity/hosting decision. Audit upstream code, fonts/icons and notices first. Say “no product telemetry” plainly; any future diagnostics should be explicit opt-in, redacted and separable from push/provider traffic.
- **Docs/onboarding:** supported-OS matrix; one quickstart; “runs with your user’s permissions”; provider billing/auth caveats; first project/model selection; service PATH/HOME diagnostics; phone setup; backup/restore/export/uninstall; troubleshooting and a redacted `doctor` report. Do not require Nix, jj deployment knowledge, a build toolchain, the operator’s DNS or his credentials to try the app.

## Recommended phases

### 0. Decide the boundary (1–2 days)

Choose first testers and their OSes; aim Linux/macOS first and Windows via WSL only if needed, **not untested native Windows support**. Choose per-user installs and provider-policy stance; neutral name/licence can precede public distribution without blocking a private pilot. Check compiled packaging feasibility for at most two days. No remote invite until the auth/security gate is addressed.

### 1. A few friends: one local install, one working task (about 10–16 days)

Use **A**, with a prebuilt web UI served from the same loopback origin as the backend, automatic browser opening and no personal backend suggestions. First run checks host tools, explains permissions/billing, signs in through the existing pi flow (only approved options), picks a repository and coordinator/worker models, then reaches the first task. Missing jj/zellij should explain limited functionality, not strand setup.

Implement the device-auth gate before exposing network access. Bundle setup/docs and explicit versioned updates; default to foreground, optional Linux/macOS user-service setup. Use Tailscale HTTPS + secure QR enrollment for the friends who need phones; web mobile first. This range assumes a constrained OS matrix and no new push infrastructure. Test on a clean machine/account for each supported OS and with two real friends, including restart/update and phone reconnect; this research did not do those tests.

If C’s spike succeeds quickly, distribute that binary through the same installer instead of requiring Bun; otherwise use pinned Bun + bundled assets and keep moving. Keep the operator’s jj watcher unchanged and separate.

### 2. Polish after pilot feedback (roughly 7–12 more days, chosen features)

Signed Android releases or Play internal testing; device management/revocation UI; optional services and startup diagnostics; explicit backup/restore; update/rollback UX; documentation fixes from real installs. Resolve notification key ownership before enabling push for independent installations. Add C’s release matrix if not already done. These estimates exclude a dedicated notification broker.

### 3. Wider sharing (separate investments)

Build Electron only if friends prefer a desktop installer or Bun setup is genuinely the main failure; reuse the same backend/config/auth rather than fork them. Add native Windows only after testing shell/PTY/workspace behavior. Offer Docker for server users and hosted UI as an optional client. Consider managed tunnelling only if Tailscale is the dominant support burden and the operator is willing to run a service.

## Decisions for the operator

1. Who are the first friends, which OSes, and is installing Bun/Tailscale acceptable?
2. Is this strictly one owner per backend, or is colleague access to another person’s backend required? Recommend one owner; shared access is a separate permissions project.
3. Which subscription integrations are approved to distribute? Keep pi OAuth, require API keys initially, or invest in official SDK/CLI adapters? T3’s approach cannot simply be copied as an authorization claim.
4. A now, C if the short spike works, desktop later—or desktop first despite higher cost?
5. Neutral public name, package/app ID, domain and licence? Open source now or after the private pilot?
6. Android signed APK versus Play internal testing? Who owns signing keys/Firebase/Play, and can push be off initially?
7. Manual stable updates versus automatic downloads; how much old-client compatibility and migration rollback to support?
8. Remain local/private with telemetry off and no hosted service, or accept ongoing tunnel/push/hosted-client operations? Recommend no new hosted infrastructure for MVP.
